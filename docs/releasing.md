# Releasing

The host and the extension release separately, each on its own tag, so either can ship without the other (ADR 0008).
[release-please](https://github.com/googleapis/release-please) cuts both: nobody bumps a version or pushes a tag by
hand.

| Train | Tag | Version | Workflows | Produces |
| --- | --- | --- | --- | --- |
| Host | `inkup-v<version>`, e.g. `inkup-v0.2.0` | `host/Cargo.toml` `[workspace.package] version` | `.github/workflows/inkup-v-release.yml` (generated by cargo-dist), which calls `desktop-macos.yml` | Archives for five targets, shell, PowerShell and Homebrew installers, checksums and the desktop app's signed, notarized DMG on the GitHub Release; the DMG's Homebrew cask |
| Extension | `inkup-extension-v<version>`, e.g. `inkup-extension-v0.1.0` | `extensions/web/package.json` "version" | `.github/workflows/release.yml` (Chrome) and `.github/workflows/firefox-release.yml` (Firefox), both started by the one tag | The Chrome zip and the Firefox zip on the GitHub Release, a Chrome Web Store upload, an addons.mozilla.org upload |

Chrome and Firefox build from the same `extensions/web` and ship the same version. The two workflows run side by side
and wait on nothing of each other's, so a slow store review holds up only its own store.

Host and extension versions are independent and will skew. What keeps a skewed pair working is the protocol contract's
breaking-change rule (ADR 0007), not matching version numbers.

## Branch rules

- `main` is protected: changes land through a pull request, and the `ci-ok` check from `.github/workflows/ci.yml` must
  pass on an up-to-date branch. `ci-ok` fails if any job it gates failed; a `changes` job skips the jobs a change
  cannot affect (the cargo matrix runs only when the host or the protocol changes). Force pushes and deletion are
  blocked; review conversations must be resolved.
- Release tags `inkup-v*`, `inkup-extension-v*`, `inkup-chrome-v*` and `inkup-firefox-v*` cannot be deleted or moved
  (a tag ruleset; see "One-time host setup"). Creating them is not restricted, which release-please relies on.
- Admins can bypass in an emergency; nobody needs an approving review because this is a one-person repo. Raise the
  approval count if collaborators join.

## How a release is cut

`.github/workflows/release-please.yml` runs on every push to `main`. For each train with releasable commits since its
last release, it keeps one release pull request open and up to date: `chore(release): inkup 0.2.0-rc.2` for the host,
`chore(release): inkup-extension 0.1.0` for the extension. The pull request bumps the version (for the host,
`host/Cargo.toml` and the host crates' entries in `host/Cargo.lock` and `apps/desktop/src-tauri/Cargo.lock`), adds the
release's section to the train's changelog (`host/CHANGELOG.md`, `extensions/web/CHANGELOG.md`), and records the version
in `.release-please-manifest.json`. `release-please-config.json` configures both trains.

1. Read the release pull request: the version and the changelog. Let CI pass.
2. Merge it (squash, like any pull request).
3. release-please, run again by the merge, tags the merge commit and creates the GitHub Release with the changelog
   section as its notes. A host release starts as a draft; dist publishes it once the artifacts are on it.
4. The tag starts the train's workflows: `inkup-v-release.yml` for the host; `release.yml` and `firefox-release.yml`
   for the extension.
5. Approve the deployments they wait on (Actions → the run → Review deployments):
   - host: `release`, for the desktop app's DMG, once the host release is out;
   - extension: `chrome-web-store`, before the Chrome Web Store upload. `firefox-amo` has no reviewer; its upload runs
     straight away.

### Which commits count

- Commit types follow Conventional Commits, and the squash commit's type is the pull request title's. `feat`, `fix`,
  `perf` and `revert` open or update a release pull request and appear in the changelog. `chore`, `ci`, `docs`,
  `test`, `refactor`, `build` and `style` do neither, unless they are breaking (`feat!:` or a `BREAKING CHANGE:`
  footer).
- Before 1.0, a `feat` bumps the minor version and a `fix` the patch; a breaking change bumps the major.
- A commit counts for the extension when it touches `extensions/web/`. It counts for the host when it touches anything
  outside `.github/`, `docs/`, `extensions/`, `fixtures/`, `packages/`, `scripts/` and `tests/`: `host/`,
  `apps/desktop/` (the DMG ships with the host), `contract/` and files at the repo root. A commit can count for both.
- A change only in `packages/` (the workspace packages the extension bundles) opens no release: it ships with the next
  extension release. release-please has no setting for extra paths.
- To force a version, put `Release-As: 0.4.0` as a footer in the squash commit's message, or set `"release-as"` on the
  package in `release-please-config.json` and take it out again once that release is out.

### Release candidates

Only the host has release candidates. Chrome accepts only dotted numbers as a manifest version, so the extension
releases stable versions only; check an extension build before release with the steps in "Checking an extension
release locally".

The host's package in `release-please-config.json` (`"."`) uses release-please's `prerelease` versioning, and its
`"prerelease"` setting picks what the release pull request proposes:

| `"prerelease"` | After `0.2.0-rc.1` | After `0.2.0` |
| --- | --- | --- |
| `true` | `0.2.0-rc.2` | `0.3.0-rc.1` after a `feat`, `0.2.1-rc.1` after a `fix` |
| `false` | `0.2.0` | `0.3.0` after a `feat`, `0.2.1` after a `fix` |

It is `true` while 0.2.0 is in release candidates. To ship the final release, set it to `false` in a pull request;
the release pull request then proposes `0.2.0`. Set it back to `true` to start the next version's candidates.

A candidate is a GitHub pre-release. Homebrew skips it (dist's formula job and `desktop-macos`'s cask step), and
`inkup update` does not offer it; the desktop app's DMG is still built, after approval.

### Without release-please

A store can still be released alone with a hand-pushed tag, e.g. to retry one store's upload at the version already on
`main`:

```sh
git switch main && git pull
git tag inkup-chrome-v0.1.0 && git push origin inkup-chrome-v0.1.0   # or inkup-firefox-v0.1.0
```

The tag must be on `main` and name the version in `extensions/web/package.json`. That store's workflow runs as for an
`inkup-extension-v` tag, and creates the GitHub Release when the tag has none.

A host release by hand needs its draft release to exist before dist uploads to it (`create-release = false`):

```sh
gh release create inkup-v0.2.0-rc.2 --draft --prerelease --target <main commit> --title inkup-v0.2.0-rc.2 --notes "…"
git tag inkup-v0.2.0-rc.2 <main commit> && git push origin inkup-v0.2.0-rc.2
```

The version must already be the one in `host/Cargo.toml`. Record it in `.release-please-manifest.json` too, or the
next release pull request proposes it again.

## The extension release

### Chrome

Chrome only installs extensions for regular users from the Chrome Web Store. A GitHub Release zip can be loaded unpacked
for development or testing, but it is not a one-click install. So a Chrome release produces both:

| Output | Where | Who can install it |
| --- | --- | --- |
| `inkup-<version>-chrome.zip` | GitHub Release for the tag | Anyone with repo access, via `chrome://extensions` → Developer mode → Load unpacked (unzip first) |
| Store submission | Chrome Web Store, unlisted | Anyone with the listing link, one click, auto-updating |

`.github/workflows/release.yml`:

- refuses tags that are not on `main` or do not end in the extensions/web/package.json version,
- runs typecheck, unit tests and `pnpm zip` with `INKUP_RELEASE_BUILD=1`, the one build with the plain icon,
- adds the zip to the tag's GitHub Release,
- uploads the zip to the Chrome Web Store and submits it for review, once the `chrome-web-store` deployment is
  approved and if store credentials are configured (otherwise it logs a notice and skips).

### Firefox

`.github/workflows/firefox-release.yml`:

- refuses tags that are not on `main` or do not end in the extensions/web/package.json version,
- runs typecheck, unit tests and `pnpm zip:firefox` with `INKUP_RELEASE_BUILD=1`, which writes the add-on zip and
  a sources zip,
- rebuilds the add-on from the sources zip and checks it matches (`scripts/verify-sources-zip.sh`),
- adds `inkup-<version>-firefox.zip` to the tag's GitHub Release,
- uploads both zips to addons.mozilla.org and submits the add-on for review, if AMO credentials are configured
  (otherwise it logs a notice and skips).

The sources zip is what AMO reviewers rebuild the bundled add-on from. It is the part of the pnpm workspace the build
reads, from the repo root: `extensions/web`, the workspace packages it imports (`packages/core`, `packages/protocol`),
the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `tsconfig.json`, and `SOURCE_BUILD.md` with the
build commands. No tests, fixtures, `host/` or `node_modules`. `zip.includeSources` in `extensions/web/wxt.config.ts`
lists it; add a path there when the build starts reading a new one, and `scripts/verify-sources-zip.sh` fails until
you do.

## The host release

The host is released by [cargo-dist](https://axodotdev.github.io/cargo-dist/) (`dist`). Its config is
`dist-workspace.toml` at the repo root; `.github/workflows/inkup-v-release.yml` is generated from it and is never
edited by hand.

The tag is dist's `<package>-v<version>` form, and the package is the `inkup` crate, so the prefix must be exactly
`inkup`, lowercase: dist and axoupdater cannot parse `InkUp-v0.2.0`. release-please's component for the host is
`inkup` for that reason. A `-` suffix such as `inkup-v0.2.0-rc.1` makes a pre-release, which skips Homebrew.

`.github/workflows/inkup-v-release.yml`:

- plans the release and fails if the tag's version is not the `inkup` crate's version,
- builds `inkup` for `aarch64-apple-darwin`, `x86_64-apple-darwin`, `aarch64-unknown-linux-gnu`,
  `x86_64-unknown-linux-gnu` and `x86_64-pc-windows-msvc`, each on a native runner, with the `dist` cargo profile,
- builds `inkup-installer.sh`, `inkup-installer.ps1`, the Homebrew formula `inkup.rb` and `sha256` checksums,
- writes `protocol-version.txt` from the `PROTOCOL_VERSION` constant, for `inkup update`'s skew guard,
- uploads all of them to release-please's draft release and publishes it (`create-release = false` in
  `dist-workspace.toml`), marking it a pre-release for a `-` version,
- pushes the formula to `liatrio-labs/homebrew-tap` (stable releases only),
- then calls `.github/workflows/desktop-macos.yml`, which waits for approval in the `release` environment and
  attaches the desktop app's DMG, then pushes its cask on a stable release
  ([The desktop app's DMG](#the-desktop-apps-dmg)).

Users install with any of:

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/liatrio-labs/inkup/releases/latest/download/inkup-installer.sh | sh
powershell -ExecutionPolicy Bypass -c "irm https://github.com/liatrio-labs/inkup/releases/latest/download/inkup-installer.ps1 | iex"
brew install liatrio-labs/tap/inkup
```

`releases/latest` works only while the newest release is a host release; an extension release made after it takes
"latest". Link a specific `inkup-v…` release in announcements. The shell and PowerShell installers also install
`inkup-update` and write an install receipt, which `inkup update` reads (ADR 0008).

### How installed hosts update

- `inkup update` installs the newest `inkup-v*` release over a copy the shell or PowerShell installer installed;
  `inkup update --check` only says whether there is one.
- A Homebrew copy asks once: leave it to `brew upgrade inkup`, or install the release anyway (a second copy in
  `~/.cargo/bin`; PATH order decides which runs). The answer is `[update] homebrew` in the data dir's config.toml;
  change it with `inkup update --homebrew brew|self|ask`.
- A `cargo install` or dev build only prints the install commands.
- Before any of these, the skew guard: when the release's `protocol-version.txt` is newer than the protocol a paired
  extension last spoke, `inkup update` names the extensions behind and asks before going on (`--yes` skips the
  question, not the warning). Update the extension first. Releases without the file are not guarded.
- The TUI and `inkup serve` check at most once a day in the background, at a terminal only, and not when `CI` or
  `INKUP_NO_UPDATE_CHECK=1` is set. A newer release shows in the TUI's key line.

To try the whole path without publishing, point the updater and the installer at a stand-in for GitHub with
`INKUP_INSTALLER_GHE_BASE_URL=http://127.0.0.1:<port>`: it must answer `/api/v3/repos/liatrio-labs/inkup/releases`
(and `/releases/latest`, and `/releases/tags/<tag>` for the skew guard) and serve the release files under
`/liatrio-labs/inkup/releases/download/<tag>/`.

### Changing the host release config

Edit `dist-workspace.toml` (or `[package.metadata.dist]` / `[profile.dist]` in the host's Cargo.toml files), then:

```sh
dist generate                  # rewrites .github/workflows/inkup-v-release.yml
dist plan --tag=inkup-v0.1.0   # what a release would build
```

Install dist at the version in `cargo-dist-version` (`brew install cargo-dist`, or its shell installer). Upgrade with
`dist init`, then bump `DIST_VERSION` and `DIST_SHA256` in `.github/workflows/host-dist-check.yml` to match. That
workflow runs `dist generate --check` and `dist plan` on pull requests that touch the host's release config. It is not
a required check.

Actions in the generated workflow are pinned by commit through `[dist.github-action-commits]`; update those pins
alongside the ones in the other workflows. zizmor findings that come from dist's template (workflow-level
`contents: write`, template expansions of the tag and dist's plan output, the plan's `container:`) are ignored for
`inkup-v-release.yml` only, in `.github/zizmor.yml`, with the reason next to each.

### The desktop app's DMG

Every host release also carries `InkUp_<version>_universal.dmg`, the desktop app for Apple silicon and Intel, signed
with Developer ID and notarized (ADR 0025). dist's release workflow calls `.github/workflows/desktop-macos.yml` once
the release is published (`post-announce-jobs = ["./desktop-macos"]` in `dist-workspace.toml`). That workflow is not
generated: edit it directly. Its one job, `desktop-macos`:

1. waits for a maintainer to approve the `release` environment (Actions → the run → Review deployments). The
   environment admits `inkup-v*` tags only and holds the secrets below;
2. runs `bundle exec fastlane mac signing` in `apps/desktop`: `setup_ci` makes a temporary default keychain, and
   `match` (read-only, `apps/desktop/fastlane/Matchfile`) installs the Developer ID Application certificate from
   `git@github.com:dbhagen/fastlane-match.git` (branch `master`, team `3K3TD4KSB2`) into it;
3. builds `tauri build --target universal-apple-darwin --bundles app,dmg` with the tag's version. Tauri signs with
   that identity and the hardened runtime, then notarizes and staples the app;
4. notarizes and staples the DMG with `xcrun notarytool`;
5. checks `codesign --verify --deep --strict` and the Developer ID authority and runtime flag on the app, and
   `spctl` on the app (`-t exec`) and the DMG (`-t install`);
6. uploads the DMG to the tag's release (`gh release upload --clobber`);
7. on a stable release only (dist's rule for the formula: the plan's announcement is not a pre-release), renders the
   Homebrew cask with `node scripts/cask.ts <version> <sha256>` and pushes it to `liatrio-labs/homebrew-tap` as
   `Casks/inkup.rb`, committed as `github-actions[bot]`. It uses the repository secret `HOMEBREW_TAP_TOKEN`, the one
   dist's formula job uses, which reaches the job through `secrets: inherit`. Nothing is pushed when the cask is
   unchanged.

The cask's token is `inkup`, the formula's too: `brew install --cask liatrio-labs/tap/inkup` installs InkUp.app and
`brew install liatrio-labs/tap/inkup` the CLI. Its `zap` removes the app's own caches and preferences
(`dev.inkup.desktop`), not the data dir the app shares with the CLI. To check a change to the cask, render it into a
throwaway local tap and audit it:

```sh
brew tap-new --no-git inkup-local/audit && mkdir -p "$(brew --repo inkup-local/audit)/Casks"
node scripts/cask.ts 0.2.0 "$(shasum -a 256 InkUp_0.2.0_universal.dmg | cut -d ' ' -f 1)" \
  > "$(brew --repo inkup-local/audit)/Casks/inkup.rb"
brew style inkup-local/audit/inkup
brew audit --cask --new inkup-local/audit/inkup   # downloads the cask's url, so that release must exist
brew untap inkup-local/audit
```

The host release is already out when this job starts, so a failed or unapproved job never blocks it. Fix the cause and
re-run the failed job: the upload replaces any earlier DMG, and the cask takes the new DMG's sha256.

Secrets, in the `release` environment:

| Secret | What it is |
| --- | --- |
| `MATCH_PASSWORD` | The match repo's passphrase |
| `MATCH_GIT_PRIVATE_KEY` | A read-only SSH deploy key for the match repo. The job writes it to a 0600 file and passes match the path |
| `APPLE_API_KEY` | The App Store Connect API key id (`5GP3ZB95LX`) |
| `APPLE_API_ISSUER` | Its issuer id |
| `APPLE_API_KEY_P8` | The key's `.p8`, base64-encoded. The job decodes it into `$RUNNER_TEMP` as `APPLE_API_KEY_PATH` |

**Proving it with a pre-release.** Merge a release candidate's release pull request (see "Release candidates"). The
release is a pre-release, so Homebrew skips it (the formula and the cask), but `desktop-macos` still runs. Approve
it, and when it is green:

```sh
gh release download inkup-v0.2.0-rc.1 -R liatrio-labs/inkup -p '*.dmg'
spctl -a -vvv -t install InkUp_0.2.0-rc.1_universal.dmg   # accepted, source=Notarized Developer ID
xcrun stapler validate InkUp_0.2.0-rc.1_universal.dmg
```

Then open the DMG, drag InkUp to Applications and open it: it should open with no Gatekeeper prompt beyond the usual
"downloaded from the Internet" confirmation.

To check the build and signing steps without the secrets, build locally with an ad-hoc identity:
`APPLE_SIGNING_IDENTITY=- pnpm -C apps/desktop tauri build --target universal-apple-darwin --bundles app,dmg`
(needs `rustup target add x86_64-apple-darwin aarch64-apple-darwin`). `codesign --verify --deep --strict` passes and
`codesign --display` shows `flags=…(adhoc,runtime)`. `spctl` rejects it, since only an Apple-issued Developer ID
certificate passes.

### Code signing the host (not set up yet)

Host binaries are unsigned. macOS Gatekeeper does not quarantine binaries fetched by the shell installer or Homebrew, but
a browser-downloaded archive will be blocked until notarised. When signing is added it plugs in here:

- macOS: dist's `macos-sign = true` setting codesigns the binaries, reading `CODESIGN_*` secrets. dist does not
  notarise; that would be a custom job (`xcrun notarytool`) added through dist's `local-artifacts-jobs` setting.
- Windows: dist's `ssldotcom-windows-sign` or `azure-windows-sign` setting, with that provider's secrets.

## One-time host setup

1. Create the public repo `liatrio-labs/homebrew-tap` (a README is enough; dist manages `Formula/`). Done: the repo
   exists.
2. Create a token that can push to it: a fine-grained personal access token (or a GitHub App token) with access to
   `liatrio-labs/homebrew-tap` only, permission **Contents: Read and write**. A classic token needs the `repo` scope.
3. Add it to this repo as the Actions secret `HOMEBREW_TAP_TOKEN`, and back it up to 1Password (secrets-backup).
4. Add a tag ruleset covering `refs/tags/inkup-v*`, `refs/tags/inkup-extension-v*`, `refs/tags/inkup-chrome-v*` and
   `refs/tags/inkup-firefox-v*` that blocks deletion and updates. Leave creation unrestricted: release-please creates
   the tags.

Until the tap and secret exist, a host release still publishes the GitHub Release; only the `publish-homebrew-formula`
job fails, and `announce` then skips.

## One-time release-please setup

A tag, release or pull request made with a workflow's `GITHUB_TOKEN` starts no other workflow. release-please therefore
runs with a personal access token, so that its tags start the release workflows and CI runs on its release pull
requests (which `ci-ok` requires before they can merge).

1. Create a fine-grained personal access token: resource owner `liatrio-labs`, repository access **Only select
   repositories** → `liatrio-labs/inkup`, repository permissions **Contents: Read and write** and **Pull requests: Read
   and write** (Metadata: Read-only comes with them). If the organization requires approval for fine-grained tokens,
   an owner approves it.
2. Add it to this repo as the Actions secret `RELEASE_PLEASE_TOKEN`, and back it up to 1Password (secrets-backup).
   Note its expiry: when it lapses, release-please fails until the secret is replaced.

Release pull requests and tags then carry the token owner's name. Without the secret, `release-please.yml` warns in its
log and falls back to `github.token`: the release pull requests still appear but get no CI run, and the tags start no
release workflow.

## One-time Chrome Web Store setup

The store API cannot create a new item, so the first upload is manual.

1. Register a Chrome Web Store developer account (one-time fee) at <https://chrome.google.com/webstore/devconsole>.
2. Download the zip from the first GitHub Release and upload it as a new item. Fill in the listing, the privacy
   practices (microphone, tab capture, `<all_urls>`: see `docs/adr/0003-all-sites-host-permission.md` and PRD P0-15),
   and set **Visibility: Unlisted**. Submit.
3. Note the **extension ID** (item page) and **publisher ID** (the dev console URL `.../devconsole/<publisher-id>`).
4. Create a Google Cloud service account for the Chrome Web Store API and download its JSON key:
   <https://developer.chrome.com/docs/webstore/service-accounts>. Add the service account's email to the publisher in
   the dev console.
5. In GitHub → Settings → Environments, create `chrome-web-store`, restrict its deployments to the tag patterns
   `inkup-extension-v*` and `inkup-chrome-v*`, and add these environment secrets. The environment already exists, with
   a required reviewer and the `inkup-chrome-v*` rule; the `inkup-extension-v*` rule and the secrets are left to add:

   | Secret | Value |
   | --- | --- |
   | `CHROME_EXTENSION_ID` | from step 3 |
   | `CHROME_PUBLISHER_ID` | from step 3 |
   | `CHROME_SERVICE_ACCOUNT_CLIENT_EMAIL` | `client_email` from the JSON key |
   | `CHROME_SERVICE_ACCOUNT_PRIVATE_KEY` | `private_key` from the JSON key |

   Back each one up to 1Password as you create it (secrets-backup). Optional repository variable
   `CHROME_SKIP_SUBMIT_REVIEW=true` uploads without submitting.

From then on every extension release uploads and submits automatically once the environment's required reviewer
approves the deployment, and Google's store review gates the new version going live. GitHub gives public repos
required reviewers for free (private repos need a paid plan); add or change reviewers under the environment's
protection rules.

## One-time addons.mozilla.org setup

AMO needs the add-on's first version uploaded by hand before the API can update it.

1. Sign in at <https://addons.mozilla.org/developers/> and submit the zip from the first Firefox GitHub Release as a new
   add-on (listed on AMO, or "On your own" for unlisted), with the sources zip when asked for source code. The add-on's
   id is the gecko id in `extensions/web/wxt.config.ts`; the workflow already sets it as `FIREFOX_EXTENSION_ID`.
2. Create API credentials at <https://addons.mozilla.org/developers/addon/api/key/>: a JWT issuer and a JWT secret.
3. In GitHub → Settings → Environments, create `firefox-amo`, restrict its deployments to the tag patterns
   `inkup-extension-v*` and `inkup-firefox-v*`, and add these environment secrets. The environment already exists,
   with the `inkup-firefox-v*` rule; the `inkup-extension-v*` rule and the secrets are left to add:

   | Secret | Value |
   | --- | --- |
   | `FIREFOX_JWT_ISSUER` | JWT issuer from step 2 |
   | `FIREFOX_JWT_SECRET` | JWT secret from step 2 |

   Back each one up to 1Password as you create it (secrets-backup). Optional repository variables:
   `FIREFOX_CHANNEL=unlisted` (the default is `listed`) and `FIREFOX_SKIP_SUBMIT_REVIEW=true`.

From then on every extension release uploads and submits automatically, and Mozilla's review gates it going live.

## Checking an extension release locally

Any build without `INKUP_RELEASE_BUILD=1` is a development build: its icons sit on black-and-yellow construction
stripes (`extensions/web/src/lib/dev-stripes.ts`). Only the release workflows set it; set it by hand to check what they
ship.

```sh
export INKUP_RELEASE_BUILD=1
pnpm zip                                    # extensions/web/.output/*-chrome.zip
pnpm zip:firefox                            # extensions/web/.output/*-firefox.zip and *-sources.zip
bash scripts/verify-sources-zip.sh --no-zip # rebuild from the sources zip in a temp dir; must match
cd extensions/web && pnpm exec wxt submit --dry-run --chrome-zip .output/*-chrome.zip
cd extensions/web && pnpm exec wxt submit --dry-run --firefox-zip .output/*-firefox.zip \
  --firefox-sources-zip .output/*-sources.zip
```
