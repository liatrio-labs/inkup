# Releasing

Every release ships the host and the extension together, with the same version on two tags (ADR 0027).
[release-please](https://github.com/googleapis/release-please) cuts it: nobody bumps a version or pushes a tag by
hand.

| Component | Tag | Version | Workflows | Produces |
| --- | --- | --- | --- | --- |
| Host | `inkup-v<version>`, e.g. `inkup-v0.7.0` | `host/Cargo.toml` `[workspace.package] version` | `.github/workflows/inkup-v-release.yml` (generated by cargo-dist), `.github/workflows/homebrew-formula.yml` and `.github/workflows/desktop-macos.yml`, all started by the one tag | Archives for five targets, shell and PowerShell installers, checksums, Homebrew bottles and the desktop app's signed, notarized DMG on the GitHub Release; the CLI's Homebrew formula and the DMG's Homebrew cask |
| Extension | `inkup-extension-v<version>`, e.g. `inkup-extension-v0.7.0` | `extensions/web/package.json` "version" | `.github/workflows/release.yml` (Chrome) and `.github/workflows/firefox-release.yml` (Firefox), both started by the one tag; `.github/workflows/chrome-web-store-sync.yml` daily | The Chrome zip and the Firefox zip on the GitHub Release, a Chrome Web Store upload (unless another version is in review), an addons.mozilla.org upload |

Chrome and Firefox build from the same `extensions/web` and ship the same version. The two workflows run side by side
and wait on nothing of each other's, so a slow store review holds up only its own store.

Every release tags and ships both, even when only one side changed. The versions match at release, but users still run
mismatched pairs for a while (the stores take days to review the extension, and either side can be held back). What
keeps such a pair working is the protocol contract's breaking-change rule (ADR 0007), not matching version numbers.

## Branch rules

- `main` is protected: changes land through a pull request, and the `ci-ok` check from `.github/workflows/ci.yml` must
  pass on an up-to-date branch. `ci-ok` fails if any job it gates failed; a `changes` job skips the jobs a change
  cannot affect (the cargo matrix runs only when the host or the protocol changes). Force pushes and deletion are
  blocked; review conversations must be resolved.
- Release tags `inkup-v*`, `inkup-extension-v*`, `inkup-chrome-v*` and `inkup-firefox-v*` cannot be deleted or moved
  (a tag ruleset; see "One-time host setup"). Creating them is not restricted, which release-please relies on.
- Admins can bypass in an emergency; nobody needs an approving review because this is a one-person repo. Raise the
  approval count if collaborators join.

## How a release is cut

`.github/workflows/release-please.yml` runs on every push to `main`. When there are releasable commits since the last
release ([Which commits count](#which-commits-count)), it keeps one release pull request open and up to date, e.g.
`chore(release): 0.8.0`, for both components.
The pull request bumps both versions to the same one (`host/Cargo.toml` and the host crates' entries in
`host/Cargo.lock` and `apps/desktop/src-tauri/Cargo.lock`; `extensions/web/package.json`), adds the release's section
to each changelog (`host/CHANGELOG.md`, `extensions/web/CHANGELOG.md`), and records both versions in
`.release-please-manifest.json`. `release-please-config.json` configures both components and links their versions
with release-please's `linked-versions` plugin.

How the version is picked: each component with releasable commits proposes its next version from its own last
release, and the plugin takes the highest for both. A component with no releasable commits of its own gets a
synthetic "Synchronize inkup versions" commit (a `Release-As` footer), so it is released at that version too, and its
changelog section lists only that line.

Nobody reviews a release; every step runs on its own:

1. release-please sets its pull request to auto-merge (squash). CI skips every job on it, so `ci-ok` passes at once:
   the code in it was tested on its own pull request. It merges within minutes of the releasable commit. To hold a
   release, turn auto-merge off on the pull request (`gh pr merge --disable-auto <number>`); it is set again on the
   next push to `main`, so close the pull request or set the component's version in the config for a longer hold.
2. The pull request merges.
3. release-please, run again by the merge, tags the merge commit `inkup-v<version>` and
   `inkup-extension-v<version>`, and creates a GitHub Release for each with its changelog section as the notes. The
   host's release starts as a draft; dist publishes it once the artifacts are on it.
4. Each tag starts its workflows: `inkup-v-release.yml` and `desktop-macos.yml` for the host; `release.yml` and
   `firefox-release.yml` for the extension.
5. The `release`, `chrome-web-store` and `firefox-amo` environments have no required reviewer. Each admits only its
   own release tags (and `chrome-web-store` also `main`, for its daily sync), and that is what keeps their secrets to
   release runs.

### Which commits count

- Commit types follow Conventional Commits, and the squash commit's type is the pull request title's. `feat`, `fix`,
  `perf` and `revert` open or update a release pull request and appear in the changelog. `chore`, `ci`, `docs`,
  `test`, `refactor`, `build` and `style` do neither, unless they are breaking (`feat!:` or a `BREAKING CHANGE:`
  footer).
- Before 1.0, a `feat` bumps the minor version and a `fix` the patch; a breaking change bumps the major.
- A release pull request opens only for a commit that ships: one of those types, or a breaking change, that touches
  `host/`, `apps/desktop/` (the DMG ships with the host), `contract/`, `packages/` (the workspace packages the
  extension and the desktop app are built from) or `extensions/web/`. `scripts/release-worthy.ts` decides, and
  `release-please.yml` runs it before release-please (ADR 0027): release-please's `exclude-paths` match directories
  only, so on its own it counted every root file (`README.md`, `pnpm-lock.yaml`) for the host, and site pull requests
  released inkup. Root files never ship on their own: a dependency change that matters edits a `package.json` or
  `Cargo.toml` in those paths too, and a lockfile-only refresh ships with the next release. To check what it would say,
  run `node scripts/release-worthy.ts`.
- Once a commit that ships is waiting, release-please picks each commit's component by path. A commit counts for the
  extension when it touches `extensions/web/`. It counts for the host when it touches anything outside `.github/`,
  `.impeccable/`, `apps/site/`, `docs/`, `extensions/`, `fixtures/`, `scripts/` and `tests/`, root files included. A
  commit can count for both. Which side it counts for decides the changelog it appears in and the version it proposes;
  either way both ship.
- To force a version, put `Release-As: 0.8.0` as a footer in a commit that counts for either component (the squash
  commit carries every commit's message, so a footer in any of the pull request's commits works). The plugin carries
  it to the other component. A `"release-as"` in `release-please-config.json` works too, but stays in force until it
  is taken out, and releases merge on their own, so prefer the footer.

### Release candidates

A release candidate covers both components: `inkup-v0.8.0-rc.1` and `inkup-extension-v0.8.0-rc.1`, both GitHub
pre-releases. `release-please-config.json` sets release-please's `prerelease` versioning for both packages at the top
level, and the top-level `"prerelease"` setting picks what the release pull request proposes:

| `"prerelease"` | After `0.8.0-rc.1` | After `0.8.0` |
| --- | --- | --- |
| `true` | `0.8.0-rc.2` | `0.9.0-rc.1` after a `feat`, `0.8.1-rc.1` after a `fix` |
| `false` | `0.8.0` | `0.9.0` after a `feat`, `0.8.1` after a `fix` |

It is `false`, so releases are stable. To start a version's candidates, set it to `true` in a pull request; to ship
the final release, set it back to `false`, and the release pull request proposes the plain version. With no `feat` or
`fix` since the last candidate, add a `Release-As: <version>` footer to that pull request's commit.

A candidate stays on GitHub:

- The host's release has dist's archives, installers and checksums and the desktop app's DMG. Homebrew skips it
  (`homebrew-formula`'s publish job and `desktop-macos`'s cask step), and `inkup update`
  does not offer it.
- The extension's release has the Chrome zip and the Firefox zip. The Chrome Web Store and addons.mozilla.org jobs
  are skipped: `scripts/extension-tag.ts` reports a `-` in the version as a pre-release, and each store job runs only
  when it is not one.
- Browsers take only dotted numbers as a manifest `version`. For `0.8.0-rc.1` the Chrome build's manifest has
  `"version": "0.8.0"` and `"version_name": "0.8.0-rc.1"` (WXT writes both from package.json). Firefox has no
  `version_name`, so its manifest has `"version": "0.8.0"` only; the zip's name, `inkup-0.8.0-rc.1-firefox.zip`, and
  the pre-release say which candidate it is. A candidate and its final release have the same manifest `version`, so
  remove a candidate you loaded by hand before installing the final one.

### Without release-please

A store can still be released alone with a hand-pushed tag, e.g. to retry one store's upload at the version already on
`main`:

```sh
git switch main && git pull
git tag inkup-chrome-v0.7.0 && git push origin inkup-chrome-v0.7.0   # or inkup-firefox-v0.7.0
```

The tag must be on `main` and name the version in `extensions/web/package.json`. That store's workflow runs as for an
`inkup-extension-v` tag, and creates the GitHub Release when the tag has none (a pre-release for a `-` version, whose
store upload is skipped).

A host release by hand needs its draft release to exist before dist uploads to it (`create-release = false`):

```sh
gh release create inkup-v0.2.0-rc.2 --draft --prerelease --target <main commit> --title inkup-v0.2.0-rc.2 --notes "…"
git tag inkup-v0.2.0-rc.2 <main commit> && git push origin inkup-v0.2.0-rc.2
```

The version must already be the one in `host/Cargo.toml`. Record it in `.release-please-manifest.json` too, or the
next release pull request proposes it again. A release by hand is one side only: the other side keeps its version, so
the next release pull request brings both to the next version again.

## The extension release

### Chrome

Chrome only installs extensions for regular users from the Chrome Web Store. A GitHub Release zip can be loaded unpacked
for development or testing, but it is not a one-click install. So a Chrome release produces both:

| Output | Where | Who can install it |
| --- | --- | --- |
| `inkup-<version>-chrome.zip` | GitHub Release for the tag | Anyone with repo access, via `chrome://extensions` → Developer mode → Load unpacked (unzip first) |
| Store submission | Chrome Web Store, unlisted | Anyone with the listing link, one click, auto-updating |

`.github/workflows/release.yml`:

- refuses tags that are not on `main` or do not end in the extensions/web/package.json version
  (`scripts/extension-tag.ts`), and notes whether the version is a pre-release,
- runs typecheck, unit tests and `pnpm zip` with `INKUP_RELEASE_BUILD=1`, the one build with the plain icon,
- adds the zip to the tag's GitHub Release,
- for a final version only, uploads the zip to the Chrome Web Store and submits it for review, in the
  `chrome-web-store` environment, if the
  store's item and publisher IDs are configured (otherwise it logs a notice and skips). It signs in to Google keyless,
  with the job's GitHub OIDC token, and calls the Chrome Web Store API v2 through `scripts/chrome-web-store.ts`.

At most one Chrome Web Store review is in flight. Before uploading, `scripts/chrome-web-store.ts` reads the item's
status (`fetchStatus`) and skips, with a notice and a green job, when:

| The store has | Then |
| --- | --- |
| A submission in review (`PENDING_REVIEW`), of any version | Skip. The store refuses an upload while an item is in review, and cancelling the review would put the item back at the end of the queue. |
| This version or newer published (`PUBLISHED`, `PUBLISHED_TO_TESTERS`) | Skip. |
| This version or newer submitted and approved but not published (`STAGED`) | Skip; publish it from the developer dashboard. |
| This version or newer submitted and `REJECTED` | Skip with a warning; fix what the review found and release a newer version. |
| This version or newer submitted and `CANCELLED` | Skip; someone cancelled it on purpose. |
| Anything else (nothing submitted, or an older version staged, rejected or cancelled) | Upload and submit. |

So a release made while another is in review reaches the store later.
`.github/workflows/chrome-web-store-sync.yml` runs daily (and from the Actions tab) on `main`: it downloads the
`inkup-<version>-chrome.zip` of the newest final `inkup-extension-v*` GitHub Release, the one `release.yml` built and
tested, and runs the same script, which submits it once the review in flight clears. Releases that came out during a
review are never submitted on their own; the newest one carries their changes. The sync and `release.yml`'s store job
share a concurrency group, so they never upload at once.

### Firefox

`.github/workflows/firefox-release.yml`:

- refuses tags that are not on `main` or do not end in the extensions/web/package.json version
  (`scripts/extension-tag.ts`), and notes whether the version is a pre-release,
- runs typecheck, unit tests and `pnpm zip:firefox` with `INKUP_RELEASE_BUILD=1`, which writes the add-on zip and
  a sources zip,
- rebuilds the add-on from the sources zip and checks it matches (`scripts/verify-sources-zip.sh`),
- adds `inkup-<version>-firefox.zip` to the tag's GitHub Release,
- for a final version only, uploads both zips to addons.mozilla.org and submits the add-on for review, if AMO
  credentials are configured
  (otherwise it logs a notice and skips).

The sources zip is what AMO reviewers rebuild the bundled add-on from. It is the part of the pnpm workspace the build
reads, from the repo root: `extensions/web`, the workspace packages it imports (`packages/core`, `packages/protocol`),
the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `tsconfig.json`, and `SOURCE_BUILD.md` with the
build commands. No tests, fixtures, `host/` or `node_modules`. `zip.includeSources` in `extensions/web/wxt.config.ts`
lists it; add a path there when the build starts reading a new one, and `scripts/verify-sources-zip.sh` fails until
you do.

## The host release

The host is released by [cargo-dist](https://axodotdev.github.io/cargo-dist/) (`dist`). Its config is
`dist-workspace.toml` at the repo root; `.github/workflows/inkup-v-release.yml` is generated from it and is never
edited by hand.

The tag is dist's `<package>-v<version>` form, and the package is the `inkup` crate, so the prefix must be exactly
`inkup`, lowercase: dist and axoupdater cannot parse `InkUp-v0.2.0`. release-please's component for the host is
`inkup` for that reason. A `-` suffix such as `inkup-v0.2.0-rc.1` makes a pre-release, which skips Homebrew.

`.github/workflows/inkup-v-release.yml`:

- plans the release and fails if the tag's version is not the `inkup` crate's version,
- builds `inkup` for `aarch64-apple-darwin`, `x86_64-apple-darwin`, `aarch64-unknown-linux-gnu`,
  `x86_64-unknown-linux-gnu` and `x86_64-pc-windows-msvc`, each on a native runner, with the `dist` cargo profile,
- builds `inkup-installer.sh`, `inkup-installer.ps1` and `sha256` checksums,
- writes `protocol-version.txt` from the `PROTOCOL_VERSION` constant, for `inkup update`'s skew guard,
- uploads all of them to release-please's draft release and publishes it (`create-release = false` in
  `dist-workspace.toml`), marking it a pre-release for a `-` version.

The same tag starts `.github/workflows/homebrew-formula.yml`, which builds Homebrew bottles from the release's archives
and publishes the formula on a stable release ([The Homebrew formula](#the-homebrew-formula)), and
`.github/workflows/desktop-macos.yml`, which runs in the `release` environment and attaches the desktop app's DMG, then
pushes its cask on a stable release ([The desktop app's DMG](#the-desktop-apps-dmg)).

Users install with any of:

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/liatrio-labs/inkup/releases/latest/download/inkup-installer.sh | sh
powershell -ExecutionPolicy Bypass -c "irm https://github.com/liatrio-labs/inkup/releases/latest/download/inkup-installer.ps1 | iex"
brew install liatrio-labs/tap/inkup
```

`releases/latest` works only while the release GitHub marks latest is the host's. Every release makes an extension
release too; dist publishes the host's draft after it, so the host's usually ends up latest, but link a specific
`inkup-v…` release in announcements. The shell and PowerShell installers also install
`inkup-update` and write an install receipt, which `inkup update` reads (ADR 0027).

### How installed hosts update

- `inkup update` installs the newest `inkup-v*` release over a copy the shell or PowerShell installer installed;
  `inkup update --check` only says whether there is one.
- A Homebrew copy asks once: leave it to `brew upgrade inkup`, or install the release anyway (a second copy in
  `~/.cargo/bin`; PATH order decides which runs). The answer is `[update] homebrew` in the data dir's config.toml;
  change it with `inkup update --homebrew brew|self|ask`.
- A `cargo install` or dev build only prints the install commands.
- Before any of these, the skew guard: when the release's `protocol-version.txt` is newer than the protocol a paired
  extension last spoke, `inkup update` names the extensions behind and asks before going on (`--yes` skips the
  question, not the warning). Update the extension first. Releases without the file are not guarded.
- The TUI and `inkup serve` check at most once a day in the background, at a terminal only, and not when `CI` or
  `INKUP_NO_UPDATE_CHECK=1` is set. A newer release shows in the TUI's key line.

To try the whole path without publishing, point the updater and the installer at a stand-in for GitHub with
`INKUP_INSTALLER_GHE_BASE_URL=http://127.0.0.1:<port>`: it must answer `/api/v3/repos/liatrio-labs/inkup/releases`
(and `/releases/latest`, and `/releases/tags/<tag>` for the skew guard) and serve the release files under
`/liatrio-labs/inkup/releases/download/<tag>/`.

### Changing the host release config

Edit `dist-workspace.toml` (or `[package.metadata.dist]` / `[profile.dist]` in the host's Cargo.toml files), then:

```sh
dist generate                  # rewrites .github/workflows/inkup-v-release.yml
dist plan --tag=inkup-v0.1.0   # what a release would build
```

Install dist at the version in `cargo-dist-version` (`brew install cargo-dist`, or its shell installer). Upgrade with
`dist init`, then bump `DIST_VERSION` and `DIST_SHA256` in `.github/workflows/host-dist-check.yml` to match. That
workflow runs `dist generate --check` and `dist plan` on pull requests that touch the host's release config. It is not
a required check.

Actions in the generated workflow are pinned by commit through `[dist.github-action-commits]`; update those pins
alongside the ones in the other workflows. zizmor findings that come from dist's template (workflow-level
`contents: write`, template expansions of the tag and dist's plan output, the plan's `container:`) are ignored for
`inkup-v-release.yml` only, in `.github/zizmor.yml`, with the reason next to each.

### The Homebrew formula

dist makes no Homebrew formula: its formula has no bottles, and Homebrew runs a formula without bottles as a source
build, which demands a current Xcode or Command Line Tools even though `install` only copies the binary (ADR 0027).
`.github/workflows/homebrew-formula.yml` publishes one with bottles instead:

1. `tag` checks the tag with `scripts/desktop-tag.ts` and decides whether the run publishes: a tag push of a stable
   release does; a pre-release, a pull request or a dry dispatch does not;
2. `bottles` waits up to 45 minutes for dist to publish the release, downloads the four macOS and Linux
   `inkup-<target>.tar.xz` archives and `sha256.sum`, and runs
   `node scripts/formula.ts <version> <archives-dir> <bottles-dir>`. That checks each archive against `sha256.sum`,
   repacks it as `inkup-<version>.<tag>.bottle.tar.gz` holding `inkup/<version>/bin/inkup` and the docs, and prints
   the formula, whose `root_url` is the release's download URL. The tags are `arm64_big_sur`, `big_sur`,
   `arm64_linux` and `x86_64_linux`;
3. `verify` installs that formula from a local tap (`brew tap-new`), with `root_url` pointed at the bottles on disk,
   on `macos-latest`, `macos-15-intel`, `ubuntu-latest` and `ubuntu-24.04-arm`. It runs `brew style`, `brew install`
   and `brew test`, and fails unless Homebrew poured the bottle, `inkup --version` is the release's, and `inkup` runs
   from `Cellar/inkup/<version>/`, where `inkup update` looks for a Homebrew copy;
4. `publish` (stable releases only) uploads the bottles to the release, checks that each downloads from `root_url`
   with the same sha256, and pushes `Formula/inkup.rb` to `liatrio-labs/homebrew-tap` as `github-actions[bot]` with
   `HOMEBREW_TAP_TOKEN`. Nothing is pushed when the formula is unchanged, and a rejected push (the cask landing first)
   rebases and retries up to 5 times.

A pull request that changes the workflow or `scripts/formula.ts` runs the first three against the newest stable host
release. To do the same for any release, or to publish a release's formula again:

```sh
gh workflow run homebrew-formula.yml -R liatrio-labs/inkup -f tag=inkup-v0.5.0                    # dry run
gh workflow run homebrew-formula.yml -R liatrio-labs/inkup -f tag=inkup-v0.5.0 -f dry_run=false   # publish
```

Publishing an older release's formula replaces the tap's newer one; don't. A failed run never touches the release
itself: fix the cause and re-run it. The bottles are replaced (`--clobber`) and the formula takes their new sha256.

To build the bottles and the formula for an existing release locally:

```sh
gh release download inkup-v0.5.0 -R liatrio-labs/inkup -p 'inkup-*.tar.xz' -p sha256.sum -D archives
node scripts/formula.ts 0.5.0 archives bottles > inkup.rb
```

The macOS tags name Big Sur, the oldest macOS Homebrew still recognises, since it pours a bottle for an older macOS
on every newer one. When Homebrew drops Big Sur, move them to its oldest remaining macOS in `scripts/formula.ts`, or
installs go back to source builds.

### The desktop app's DMG

Every host release also carries `InkUp_<version>_universal.dmg`, the desktop app for Apple silicon and Intel, signed
with Developer ID and notarized (ADR 0025). `.github/workflows/desktop-macos.yml` builds it. It is not generated by
dist and not part of dist's workflow: it runs on the same `inkup-v*` tag push, so it runs for release candidates too.
(It was a dist `post-announce-jobs` job at first, and a pre-release skipped it: dist skipped its Homebrew publish job
for a pre-release, and a job whose ancestor was skipped is skipped too.) Its `tag` job runs
`node scripts/desktop-tag.ts <tag> <remote>`, which fails unless the tag is a host release tag
(`inkup-v<major>.<minor>.<patch>`, with an optional `-<pre-release>`) that exists on the remote, and prints its
version, whether it is a pre-release (a `-` in the version, the rule dist and release-please use) and the commit it
points at. Its `desktop-macos` job then:

1. runs in the `release` environment, which admits `inkup-v*` tags only and holds the secrets below, and checks out
   the commit the tag points at;
2. runs `bundle exec fastlane mac signing` in `apps/desktop`: `setup_ci` makes a temporary default keychain, and
   `match` (read-only, `apps/desktop/fastlane/Matchfile`) installs the Developer ID Application certificate from
   `git@github.com:dbhagen/fastlane-match.git` (branch `master`, team `3K3TD4KSB2`) into it;
3. builds the `inkup` CLI for both architectures and lipos them (`scripts/desktop-cli.sh --release --universal`), then
   `tauri build --target universal-apple-darwin --bundles app,dmg --config src-tauri/tauri.cli.conf.json` with the
   tag's version, which bundles that CLI at `InkUp.app/Contents/MacOS/inkup` (Tauri's `externalBin`). Tauri signs the
   app and the CLI with that identity and the hardened runtime, then notarizes and staples the app;
4. notarizes and staples the DMG with `xcrun notarytool`;
5. checks `codesign --verify --deep --strict` and the Developer ID authority and runtime flag on the app and on its
   bundled CLI, `spctl` on the app (`-t exec`) and the DMG (`-t install`), that the CLI has both architectures, and
   that its `--version` is the tag's;
6. uploads the DMG to the tag's release (`gh release upload --clobber`). release-please creates that release as a
   draft and dist's `host` job publishes it; the upload works on the draft, and this job never publishes it. If the
   release does not exist yet, it checks every 30 seconds for up to 30 minutes, then fails;
7. on a stable release only (the formula's rule too), waits up to 30 minutes for dist to publish the release,
   because the cask's url only downloads from a published release. It then renders the Homebrew cask with
   `node scripts/cask.ts <version> <sha256>` and pushes it to `liatrio-labs/homebrew-tap` as `Casks/inkup.rb`,
   committed as `github-actions[bot]`. It uses the repository secret `HOMEBREW_TAP_TOKEN`, the one
   `homebrew-formula.yml` uses. Nothing is pushed when the cask is unchanged, and a rejected push (the formula landing
   first) rebases and retries up to 5 times.

Only one run per tag goes at a time; a second waits instead of cancelling the first. It restores no dependency
caches, as a release build.

To build the DMG for a tag that already exists (a failed run you would rather start over, or a release that has
none), dispatch the workflow on that tag:

```sh
gh workflow run desktop-macos.yml -R liatrio-labs/inkup --ref inkup-v0.2.0 -f tag=inkup-v0.2.0
```

`--ref` must be the tag, not `main`: the `release` environment admits `inkup-v*` tags only, and a dispatched run's ref
is the one it was dispatched on. The tag must also contain this version of `desktop-macos.yml` (the
`workflow_dispatch` trigger), so tags from before it (`inkup-v0.2.0-rc.2` and earlier) can't be built this way.

The cask's token is `inkup`, the formula's too: `brew install --cask liatrio-labs/tap/inkup` installs InkUp.app and
`brew install liatrio-labs/tap/inkup` the CLI. Its `zap` removes the app's own caches and preferences
(`dev.inkup.desktop`), not the data dir the app shares with the CLI. To check a change to the cask, render it into a
throwaway local tap and audit it:

```sh
brew tap-new --no-git inkup-local/audit && mkdir -p "$(brew --repo inkup-local/audit)/Casks"
node scripts/cask.ts 0.2.0 "$(shasum -a 256 InkUp_0.2.0_universal.dmg | cut -d ' ' -f 1)" \
  > "$(brew --repo inkup-local/audit)/Casks/inkup.rb"
brew style inkup-local/audit/inkup
brew audit --cask --new inkup-local/audit/inkup   # downloads the cask's url, so that release must exist
brew untap inkup-local/audit
```

dist's workflow waits on nothing here, so a failed job never blocks the host release. Fix the cause and
re-run the failed job: the upload replaces any earlier DMG, and the cask takes the new DMG's sha256.

Secrets, in the `release` environment:

| Secret | What it is |
| --- | --- |
| `MATCH_PASSWORD` | The match repo's passphrase |
| `MATCH_GIT_PRIVATE_KEY` | A read-only SSH deploy key for the match repo. The job writes it to a 0600 file and passes match the path |
| `APPLE_API_KEY` | The App Store Connect API key id (`5GP3ZB95LX`) |
| `APPLE_API_ISSUER` | Its issuer id |
| `APPLE_API_KEY_P8` | The key's `.p8`, base64-encoded. The job decodes it into `$RUNNER_TEMP` as `APPLE_API_KEY_PATH` |

**Proving it with a pre-release.** Merge a release candidate's release pull request (see "Release candidates"). The
release is a pre-release, so Homebrew skips it (the formula and the cask), but `desktop-macos.yml` still runs. When it is

Then open the DMG, drag InkUp to Applications and open it: it should open with no Gatekeeper prompt beyond the usual

### Code signing the host (not set up yet)

Host binaries are unsigned. macOS Gatekeeper does not quarantine binaries fetched by the shell installer or Homebrew, but
a browser-downloaded archive will be blocked until notarised. When signing is added it plugs in here:

- macOS: dist's `macos-sign = true` setting codesigns the binaries, reading `CODESIGN_*` secrets. dist does not
  notarise; that would be a custom job (`xcrun notarytool`) added through dist's `local-artifacts-jobs` setting.
- Windows: dist's `ssldotcom-windows-sign` or `azure-windows-sign` setting, with that provider's secrets.

## One-time host setup

1. Create the public repo `liatrio-labs/homebrew-tap` (a README is enough; `homebrew-formula.yml` manages `Formula/`
   and `desktop-macos.yml` `Casks/`). Done: the repo exists.
2. Create a token that can push to it: a fine-grained personal access token (or a GitHub App token) with access to
   `liatrio-labs/homebrew-tap` only, permission **Contents: Read and write**. A classic token needs the `repo` scope.
3. Add it to this repo as the Actions secret `HOMEBREW_TAP_TOKEN`, and back it up to 1Password (secrets-backup).
4. Add a tag ruleset covering `refs/tags/inkup-v*`, `refs/tags/inkup-extension-v*`, `refs/tags/inkup-chrome-v*` and
   `refs/tags/inkup-firefox-v*` that blocks deletion and updates. Leave creation unrestricted: release-please creates
   the tags.

Until the tap and secret exist, a host release still publishes the GitHub Release; only `homebrew-formula.yml`'s
`publish` job and `desktop-macos.yml`'s cask step fail.

## One-time release-please setup

A tag, release or pull request made with a workflow's `GITHUB_TOKEN` starts no other workflow. release-please therefore
runs with a personal access token, so that its tags start the release workflows and CI runs on its release pull
requests (which `ci-ok` requires before they can merge).

1. Create a fine-grained personal access token: resource owner `liatrio-labs`, repository access **Only select
   repositories** → `liatrio-labs/inkup`, repository permissions **Contents: Read and write** and **Pull requests: Read
   and write** (Metadata: Read-only comes with them). If the organization requires approval for fine-grained tokens,
   an owner approves it.
2. Add it to this repo as the Actions secret `RELEASE_PLEASE_TOKEN`, and back it up to 1Password (secrets-backup).
   Note its expiry: when it lapses, release-please fails until the secret is replaced.

Release pull requests and tags then carry the token owner's name. Without the secret, `release-please.yml` warns in its
log and falls back to `github.token`: the release pull requests still appear but get no CI run, and the tags start no
release workflow.

## One-time Chrome Web Store setup

The release job signs in to Google without a key: GitHub's OIDC token for the job is exchanged through workload
identity federation for a short-lived access token of a service account the store publisher trusts. Liatrio's Google
Cloud organization blocks service account key creation, so there is no JSON key and no key secret.

### What already exists

| Piece | Value |
| --- | --- |
| Google Cloud project | `inkup-cws` (number `600628809675`), Chrome Web Store API enabled |
| Service account | `inkup-cws-upload@inkup-cws.iam.gserviceaccount.com` |
| Workload identity pool and provider | `projects/600628809675/locations/global/workloadIdentityPools/github/providers/liatrio-labs-inkup` |
| Provider issuer | `https://token.actions.githubusercontent.com` |
| Provider condition | repository owner id `223510100`, repository id `1385938436`, environment `chrome-web-store` |
| Binding | `roles/iam.workloadIdentityUser` on the service account for the subject `repo:liatrio-labs@223510100/inkup@1385938436:environment:chrome-web-store` |
| GitHub environment | `chrome-web-store`, admits `inkup-extension-v*` and `inkup-chrome-v*` tags and the `main` branch (for `chrome-web-store-sync.yml`), no required reviewer |

The repo uses GitHub's immutable OIDC subject format, with the owner and repository ids after `@`, so renaming the repo
or the organization does not hand its identity to a new one. The provider's condition checks the repository and the
environment, not the ref, so `release.yml` on a tag and `chrome-web-store-sync.yml` on `main` sign in the same way. Both
name the provider and the service account in plain text; neither is a secret.

To rebuild it from nothing (after `gcloud projects create inkup-cws`, linking billing, and
`gcloud services enable chromewebstore.googleapis.com iam.googleapis.com iamcredentials.googleapis.com sts.googleapis.com`):

```sh
gcloud iam service-accounts create inkup-cws-upload --project=inkup-cws

gcloud iam workload-identity-pools create github --project=inkup-cws --location=global \
  --display-name="GitHub Actions"

gcloud iam workload-identity-pools providers create-oidc liatrio-labs-inkup --project=inkup-cws \
  --location=global --workload-identity-pool=github \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.repository_id=assertion.repository_id,attribute.environment=assertion.environment,attribute.ref=assertion.ref" \
  --attribute-condition="assertion.repository_owner_id == '223510100' && assertion.repository_id == '1385938436' && assertion.environment == 'chrome-web-store'"

gcloud iam service-accounts add-iam-policy-binding inkup-cws-upload@inkup-cws.iam.gserviceaccount.com \
  --project=inkup-cws --role=roles/iam.workloadIdentityUser \
  --member="principal://iam.googleapis.com/projects/600628809675/locations/global/workloadIdentityPools/github/subject/repo:liatrio-labs@223510100/inkup@1385938436:environment:chrome-web-store"
```

### What is left for a maintainer

The store API cannot create a new item, so the first upload is manual.

1. Register a Chrome Web Store developer account (one-time fee) at <https://chrome.google.com/webstore/devconsole>.
2. Download the zip from the first GitHub Release and upload it as a new item. Fill in the listing, the privacy
   practices (microphone, tab capture, `<all_urls>`: see `docs/adr/0003-all-sites-host-permission.md` and PRD P0-15),
   and set **Visibility: Unlisted**. Submit.
3. Note the **extension ID** (item page) and **publisher ID** (the dev console URL `.../devconsole/<publisher-id>`).
4. In the dev console's account settings, add `inkup-cws-upload@inkup-cws.iam.gserviceaccount.com` as the publisher's
   service account: <https://developer.chrome.com/docs/webstore/service-accounts>.
5. In GitHub → Settings → Environments → `chrome-web-store`, add these environment secrets:

   | Secret | Value |
   | --- | --- |
   | `CHROME_EXTENSION_ID` | from step 3 |
   | `CHROME_PUBLISHER_ID` | from step 3 |

   Neither is a credential, but keeping them in the environment keeps them to release tags and the sync on `main`.
   Optional repository variable `CHROME_SKIP_SUBMIT_REVIEW=true` uploads without submitting.

From then on every final release uploads and submits automatically, unless another version is in review (then the
daily sync submits the newest release once it clears), and Google's store review gates the new version going live.
Until both secrets are set, the job logs a notice and skips. To gate uploads on a person again, add a required reviewer
under the environment's protection rules (free on public repos).

## One-time addons.mozilla.org setup

AMO needs the add-on's first version uploaded by hand before the API can update it.

1. Sign in at <https://addons.mozilla.org/developers/> and submit the zip from the first Firefox GitHub Release as a new

3. In GitHub → Settings → Environments, create `firefox-amo`, restrict its deployments to the tag patterns

## Checking an extension release locally

Any build without `INKUP_RELEASE_BUILD=1` is a development build: its icons sit on black-and-yellow construction
stripes (`extensions/web/src/lib/dev-stripes.ts`). Only the release workflows set it; set it by hand to check what they
ship.

```sh
export INKUP_RELEASE_BUILD=1
pnpm zip                                    # extensions/web/.output/*-chrome.zip
pnpm zip:firefox                            # extensions/web/.output/*-firefox.zip and *-sources.zip
bash scripts/verify-sources-zip.sh --no-zip # rebuild from the sources zip in a temp dir; must match
cd extensions/web && pnpm exec wxt submit --dry-run --firefox-zip .output/*-firefox.zip \
  --firefox-sources-zip .output/*-sources.zip
```
